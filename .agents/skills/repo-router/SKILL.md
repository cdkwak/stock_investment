# Repository Router

Use the narrowest authoritative route before acting:

1. Read `AGENTS.md`, then `docs/project/PROJECT_STATUS.md`.
2. Read the one domain Status owning the assigned task. Read multiple domain
   Status documents only when the task explicitly crosses their interfaces;
   Project Status permits disjoint domain work to proceed in parallel.
3. For an existing routed task, expand only to the Status-selected contract,
   checkpoint, source record, or active runbook.
4. Read `REPOSITORY_MAP.md` only to locate ownership or modification boundaries; read the roadmap only for sequencing decisions.

For a new direct or standing-authorized task, establish the minimum missing
contract/evidence/runbook rather than requiring it to be pre-selected by Status.
Status is factual routing authority, not a fresh phase-approval mechanism.

Do not treat archives, inventories, or a broad repository scan as current
authority. For review or status work, remain read-only. For implementation,
make the smallest coherent change and validate it proportionately. Standing
Project/Data authorization covers ordinary engineering plus public/existing-
credential API and read-only account operations. Missing identity, schema,
rights, finality, or PIT evidence gates only the unsupported claim or dependent
promotion; investigate it autonomously and continue independent work. Block the
whole task only for an unavailable required secret/entitlement, rejected
protected-resource escalation, exact future provider
publication/session/cooldown time, or a user-only financial/legal/access action
after no safe in-scope action remains. A timed wait releases its writer lane and
secret values are never requested through chat/logs. Never recreate
permission-only phase, activation, retry-zero, manual-only, or fresh-approval
gates from older evidence.
